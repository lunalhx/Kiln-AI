# Spec: Delayed Review cadence and Durable milestone

## Problem Statement

Kiln-AI's current product path ends when a learner passes a fresh Independent Test. That pass can establish Independent Evidence, but it creates no durable work for checking whether the capability survives after assistance and time have faded. Delayed Review is therefore present in the accepted learning model but absent from the runnable product.

As a result, a learner cannot discover or start due Review work, the fixed Review Cadence never advances, and no evidence sequence can establish the Durable Mastery Milestone. Current Milestone and Highest Milestone Reached exist as projections, but the highest possible end-to-end result is Independent. This leaves the invariant Delayed Review stage from ADR-0004, the evidence-derived milestone model from ADR-0007, and the scheduling contract from ADR-0029 disconnected from the current Apply vertical slice.

The missing layer must remain small. Kiln-AI already has the mechanisms needed to generate a Fresh Equivalent Task, validate and verify it before delivery, assess a formal no-hint response, persist a Task Attempt, accept Learning Evidence, protect private assessor facts, and recover an Apply Flow durably. The product needs durable Review work and cadence orchestration around those mechanisms, not a second assessment stack or a background Agent.

## Solution

Add a durable Review Task entity with the lifecycle Scheduled, Due, Started, Completed, or Cancelled. When a fresh Independent Test produces accepted no-hint passing evidence, Kiln-AI atomically creates the first Review Task for the same learner, Target Concept, and original Learning Flow, due 24 hours after the Independent completion. A conventional scheduler idempotently changes Scheduled tasks whose `dueAt` has arrived to Due. The scheduler performs no model call, creates no Task Package or Task Attempt, and does not resume the Apply Flow.

Expose unfinished Review Tasks to the learner and allow only a Due task to be started. An explicit learner-confirmed cancellation can stop an unfinished cadence without claiming a learning result. Starting a Due task resumes the original durable Apply Flow in Delayed Review and generates a verified Fresh Equivalent Task just in time. Review uses the existing Apply Profile, frozen Skill Stack, Task Package, Output Gate, Task Verification, Assessment, selective Response Verification, Task Attempt, Artifact Store, Exposure Ledger, submission, idempotency, and evidence rules. The only new generation artifact is one frozen, versioned Review Task Blueprint with `Attempt Purpose = Review` and novelty exclusions covering every previously exposed task and solution fingerprint in the Flow.

A conclusive no-hint Review pass completes the current Review Task and schedules the next task 3, 7, and then 21 days after the actual Review completion time. The fourth successful Review creates the evidence needed to project Current Milestone and Highest Milestone Reached as Durable and schedules nothing further. A missed Review remains Due. A conclusive valid Review failure records Review failure evidence, completes the current Review Task, cancels any other unfinished Review work defensively, projects Current Milestone to Learning while preserving Highest Milestone Reached, and stops the cadence. A later fresh Independent pass starts a new cadence at the one-day step.

## User Stories

1. As a learner who has demonstrated Independent capability, I want a Review Task to be scheduled automatically, so that I do not need to remember when to test retention.
2. As a learner, I want to see my unfinished Review work and its due time, so that I know what is upcoming and what is ready now.
3. As a learner, I want a Scheduled Review Task to be non-startable before its due time, so that early practice is not mistaken for delayed evidence.
4. As a learner, I want a Review Task to become Due when its due time arrives, so that it appears in my actionable work without manual rescheduling.
5. As a learner, I want an overdue Review Task to remain Due, so that missing the intended time does not silently discard the retention check.
6. As a learner, I want repeated scheduler runs to leave me with one actionable Review Task for a Concept, so that I never receive duplicate or stacked work.
7. As a learner, I want starting a Due Review Task to produce the task at that moment, so that the assessment is fresh rather than prepared or exposed in advance.
8. As a learner, I want each Review to use a Fresh Equivalent Task, so that passing reflects retained capability rather than recognition of an earlier question or answer.
9. As a learner, I want Review to use the same bounded, no-hint Apply interaction I already know, so that delayed assessment does not introduce a second task experience.
10. As a learner, I want every Review task verified before I see it, so that an invalid generated instrument cannot affect my milestone.
11. As a learner, I want expected answers, source traces, Task Fingerprints, assessment facts, and model reasoning to remain private during Review, so that the task remains independent.
12. As a learner, I want one formal submission to close each displayed Review attempt, so that editing after an outcome cannot manufacture stronger evidence.
13. As a learner, I want a successful first Review to schedule the next Review three days after I actually complete it, so that lateness does not compress the next interval.
14. As a learner, I want later successful Reviews to schedule the next checks seven and then twenty-one days after actual completion, so that the accepted cadence is followed exactly.
15. As a learner, I want passing the fourth Review to establish Durable, so that the product recognizes capability retained across the complete cadence.
16. As a learner, I want no further Review Task after Durable is established, so that the finite Phase 0 cadence has a clear end.
17. As a learner, I want to see both Current Milestone and Highest Milestone Reached, so that current guidance and historical achievement are not conflated.
18. As a learner, I want a conclusive Review failure to move Current Milestone back to Learning without erasing Highest Milestone Reached, so that guidance is honest without deleting prior achievement.
19. As a learner, I want evaluator uncertainty to leave my milestone and cadence position unchanged and give me a fresh equivalent Review attempt, so that system uncertainty is not recorded as my failure.
20. As a learner, I want a temporary Source Gap or exhausted task-generation attempt to leave my Review work available for retry, so that infrastructure failure does not consume the cadence step.
21. As a learner, I want to explicitly cancel an unfinished Review Cadence, so that I can intentionally end the retention plan without fabricating pass, failure, or a milestone change.
22. As a learner, I want a restarted application to recover the same Review Task and open Review attempt, so that durable review work survives process loss.
23. As an operator, I want Review due-state scheduling to run without any model invocation, so that time-based orchestration is cheap, predictable, and auditable.
24. As an operator, I want the cadence fixed at 1, 3, 7, and 21 days, so that Phase 0 behavior is deterministic and has no unvalidated tuning surface.
25. As an operator, I want at most one unfinished Review Task per learner and Concept, so that retries, scheduler overlap, and repeated Independent evidence cannot stack work.
26. As an operator, I want Review Tasks ordered by due time when surfaced, so that the oldest overdue work is handled first.
27. As an operator, I want every Review Task transition, generated package, verification, Attempt, assessment, response verification, exposure, and evidence record retained, so that Durable can be audited and rebuilt.
28. As an operator, I want Review start and submission commands to be idempotent, so that retries cannot create duplicate Task Packages, Attempts, evidence, or future Review Tasks.
29. As a platform developer, I want one purpose-specific Review Blueprint to reuse the Apply Profile and frozen Skill Stack, so that Review adds policy data rather than a parallel Profile hierarchy.
30. As a platform developer, I want cadence metadata to remain application-owned and outside the model context, so that a model cannot choose a review interval, task status, or milestone.
31. As a platform developer, I want the Review invocation to receive only the approved Concept data, Review Blueprint, source passages, Learner Locale, and complete novelty exclusions, so that prior answers, rationales, feedback, and expected answers cannot leak into the new task.
32. As a platform developer, I want accepted Learning Evidence to remain the source of truth for Concept Progress, so that the scheduler and Review Task table cannot directly award Independent or Durable.
33. As a platform developer, I want the Concept Progress projector to derive four consecutive qualifying Review successes after the latest Independent success, so that Durable is deterministic and rebuildable.
34. As a platform developer, I want a conclusive no-hint Review failure represented as accepted failure evidence, so that the downgrade is evidence-backed rather than an imperative milestone mutation.
35. As a platform developer, I want evidence acceptance and its Review Task/cadence transition committed atomically, so that recovery cannot observe evidence without the correct next work item or vice versa.
36. As a platform developer, I want concurrent scheduler and learner commands guarded by durable state transitions and uniqueness constraints, so that only one caller can advance a Review Task.
37. As a platform developer, I want time supplied through the existing Clock boundary, so that the entire cadence can be tested deterministically without sleeping.
38. As a platform developer, I want Review submissions to reuse the existing Apply submission contract, so that private-field protection, canonical-answer confirmation, conflict behavior, and recovery stay consistent.
39. As a platform developer, I want the current application-owned Learning StateGraph to resume the original durable Apply Flow in Delayed Review without adding another graph runtime or Blackboard model, so that this feature follows the repository's accepted runtime baseline.

## Implementation Decisions

- This is a narrow extension of the existing Apply vertical slice. It adds Review work orchestration, one Review Blueprint, learner-facing Review discovery/start behavior, Review evidence projection, and the persistence needed to make that path durable. It does not add a Review Profile, Review Agent, new Skill Bundle, or second graph runtime; it reuses the application-owned Learning StateGraph command boundary already accepted for Learning/Practice.
- Review Task is an application-owned durable work item, not a Task Package. Its minimum persisted identity is Review Task ID, learner ID, Concept ID, original Learning Flow ID, review number from 1 through 4, status, due time, creation time, and the applicable started/completed/cancelled timestamps. Generated learner text, answers, Rubrics, and model artifacts remain in the existing Task Package, Task Attempt, and Artifact Store boundaries.
- Review Task status is closed to Scheduled, Due, Started, Completed, and Cancelled. The normal success path is Scheduled to Due to Started to Completed. Cancellation is terminal. Completed and Cancelled tasks remain available for audit but are never actionable.
- The database enforces at most one unfinished Review Task for a learner and Concept across Scheduled, Due, and Started states. Cadence transitions also check this invariant in the domain so the in-memory and PostgreSQL implementations behave identically.
- Review number is durable scheduling metadata. Review 1 follows Independent success by 1 day; successful Reviews 1, 2, and 3 create Reviews 2, 3, and 4 after 3, 7, and 21 days respectively. Review 4 success creates no successor.
- Every “day” in the Phase 0 cadence is an exact 24-hour duration over `Instant`. The first due time is the accepted Independent completion time plus 24 hours. Each later due time is the accepted Review completion time plus its next interval. Due times are never calculated from the first Independent date or the previous scheduled due time.
- The fixed cadence is domain policy, not operator or learner configuration. Scheduler polling frequency is operational and does not alter `dueAt`; a task becomes eligible whenever `dueAt <= now`.
- A conventional trigger-layer scheduler invokes one deterministic due-transition use case. It updates eligible Scheduled rows to Due with a conditional, concurrency-safe operation. It performs no model call, Apply execution, Task Verification, Task Package creation, Task Attempt creation, evidence acceptance, or learner-flow resume.
- Repeated scheduler ticks are idempotent. A missed task remains Due indefinitely. No scheduler tick creates a successor Review Task; successors are created only by qualifying evidence completions.
- The learner-facing Review Task collection returns unfinished tasks for the supplied learner, ordered by due time. It exposes Review Task ID, Concept ID, status, review number, and due time plus a safe Concept Progress projection. Only Due tasks advertise a start action. Every unfinished task advertises explicit cancellation after learner confirmation; Scheduled work may be shown as upcoming but cannot be started.
- The reference learner UI retains its Phase 0 learner identity across reloads, shows unfinished Review work, enables start only for Due work, and displays Current Milestone separately from Highest Milestone Reached. Authentication and a general learner-account model remain outside this spec.
- Starting a Review is an idempotent command identified by the existing `Idempotency-Key` convention. A replay of the same key and payload returns the original result. A different command racing or attempting to start an already Started, Completed, Cancelled, or not-yet-Due task cannot create a second package or attempt.
- Review task generation and Task Verification occur before the durable Review Task changes from Due to Started. If generation ends in Source Gap, Task Generation Exhausted, or provider/configuration unavailability, no Attempt or exposure is created and the Review Task remains Due. The existing Flow commits the safe Unavailable Interaction and Pending Operation of ADR-0069, so bounded `retry_requested` can resume the due Review without a client re-sending the start operation.
- After a Task Package passes the existing Output Gate and isolated Task Verification, the implementation durably binds the new Review Attempt to the Review Task, records exposure, advances the original Learning Flow to a learner interaction in Delayed Review, and changes the Review Task to Started. Recovery returns that exact interaction rather than generating a replacement.
- A Started Review Task remains the one cadence work item until it receives a conclusive pass or failure. If response assessment is inconclusive under the existing deterministic and selective-verification rules, Kiln-AI accepts no evidence, changes no milestone or cadence position, and produces a new verified Fresh Equivalent Review attempt for the same Started Review Task. If that replacement cannot be prepared, the work remains Started and resumable without being counted as pass or failure.
- `POST /api/review-tasks/{reviewId}/cancel` is an idempotent, explicit cadence operation. It marks Scheduled or Due work Cancelled. For Started work it atomically abandons the open Review Attempt, cancels the Review Task, and commits a terminal Flow transition. Cancellation accepts no Evidence, changes neither Current Milestone nor Highest Milestone Reached, and releases the learner+Concept Active Learning Work claim. Replays and repeated cancellation of a Completed or Cancelled Review Task return the committed terminal state without a new effect.
- Review uses the same one-formal-submission Apply response contract as Independent Test. The formal submission closes its Task Attempt before Assessment. Duplicate or stale submissions preserve the existing conflict and idempotency behavior.
- Add one frozen `kiln.task-blueprint/v1` Review Blueprint for the existing polynomial-differentiation reference. It keeps the Independent Blueprint's Concept, Mastery Rubric criteria, source grounding, task shape, mathematical scope, notation, answer representation, response fields, and comparable difficulty. It changes `attempt_purpose` to `review`, uses the Review final-derivative assessment policy, and excludes all task and solution fingerprints previously exposed in the original Flow.
- The Review Blueprint uses the existing Apply Profile and the same frozen five-Bundle Skill Stack. No Bundle gains scheduler, milestone, or cadence authority. Cadence step and due metadata are not supplied to the generator because they are not needed to create an equivalent task.
- Every Review Task Package follows the existing two-projection visibility contract and the full generation retry policy. Task Verification remains isolated from generation; learner-response Assessment remains isolated from both. The learner projection never exposes expected answers, private source data, Fingerprints, execution trace, assessment facts, or model reasoning.
- A qualifying Review success is a conclusive pass from a valid Review Attempt with no assistance, under the same final-expression and non-contradictory optional-rationale policy as Independent Test. It creates one accepted Review PASS evidence record.
- A qualifying Review failure is a conclusive fail from a valid no-assistance Review Attempt after the existing deterministic and selective Response Verification rules have resolved the outcome. It creates one accepted Review FAIL evidence record. Inconclusive assessment, abandoned attempts, invalid submissions, Source Gap, Task Generation Exhausted, and system errors create neither pass nor failure evidence.
- Independent evidence acceptance and first-Review scheduling form one transactional domain transition. Review pass acceptance, current-task completion, and successor scheduling form one transactional transition. Review failure acceptance, current-task completion, and defensive cancellation of any other unfinished work form one transactional transition. Each transition is exactly-once per Task Attempt.
- A new fresh Independent success cancels any stale unfinished Review Task for the learner and Concept, resets the Review success count, and schedules Review 1 after one day. This is the restart point after remediation and also preserves the one-unfinished-task invariant.
- Concept Progress remains a deterministic fold over accepted Learning Evidence ordered by acceptance time. A qualifying Independent PASS establishes at least Independent and starts a Review-success count at zero. Each qualifying Review PASS advances the consecutive count. Counts one through three keep Current Milestone at Independent; count four projects Durable. A qualifying Review FAIL resets the count and projects Current Milestone to Learning.
- Highest Milestone Reached is the maximum milestone ever reached during the evidence fold and never decreases. A later Review failure can therefore produce Current Milestone = Learning and Highest Milestone Reached = Independent or Durable. Scheduling records never directly modify either value.
- Concept Progress projects the Delayed Review stage while Current Milestone is Independent or Durable, and Learning and Practice after a qualifying Review failure. The failure transition exposes the existing safe continuation/remediation boundary; implementing the future Pedagogy Agent or additional Teaching Profiles is not part of this spec.
- The original durable Apply Flow is reused. Review start appends a new learner interaction for the same Flow in Delayed Review through the existing application-owned Learning StateGraph, and Review submission continues through the existing flow command endpoint. A separate Flow, graph checkpoint model, or background model process is not introduced.
- Add a minimal Review Task API for collection, start, and explicit cancellation. The collection is learner-safe. Start returns the same learner-facing Apply flow representation used by current start/query/submit behavior. Cancellation returns its committed learner-safe review/progress state and, for Started work, the terminal Flow boundary. Review answers continue through the existing Apply submission contract. Public responses may add the safe Concept Progress view but never private assessor data.
- Extend the current baseline product schema directly. There is no backfill, compatibility path, or migration behavior for historical Independent completions because the project explicitly does not preserve backward compatibility; only Independent evidence accepted after this feature exists starts a cadence.

## Testing Decisions

- A good test observes learner-visible work, durable state, evidence, and projected milestones through public use cases or HTTP contracts. It does not assert scheduler implementation details, repository call order, prompt wording, private helper classes, or internal transaction structure.
- The primary acceptance seam is one deterministic Delayed Review loop contract around the durable Apply and Review use cases with scripted generation, Task Verification, Assessment, Response Verification, and a controllable Clock. This is the highest seam that can validate the complete cadence without live-model variability.
- The main success scenario starts from an accepted Independent pass, asserts exactly one Scheduled Review 1 at completion plus 24 hours, advances the Clock, runs the due transition, starts a verified fresh Review, and repeats successful completion at 3-, 7-, and 21-day intervals. It ends with four Review PASS evidence records, Current Milestone = Durable, Highest Milestone Reached = Durable, and no unfinished Review Task.
- Cadence assertions use the actual completion instant of each qualifying attempt. The test deliberately completes at least one Review late and confirms that the next `dueAt` is based on the late completion rather than the earlier scheduled time.
- The contract covers pre-due non-actionability/non-startability, repeated scheduler ticks, overdue tasks remaining Due, due-time ordering, and the invariant of at most one unfinished Review Task per learner and Concept.
- The contract covers idempotent Review start and submission replays, a concurrent or different-key second start, stale interaction versions, duplicate submissions, exactly one Task Package/Attempt per successful start, exactly one evidence record per conclusive attempt, and exactly one successor Review Task.
- The contract confirms that every Review task is generated only after start, has Attempt Purpose Review, passes Task Verification before exposure, and excludes all Diagnostic, Independent, and prior Review task/solution fingerprints from the same Flow.
- The contract confirms least-privilege Review generation context: no prior learner answer, rationale, assessment result, feedback, expected answer, or source-private artifact reaches the Apply generation model.
- The contract covers Source Gap, provider/configuration unavailability, first-candidate Task Verification rejection followed by success, malformed verification, two failed generation cycles, bounded unavailable retry, and start recovery. No failed generation creates an Attempt or exposure, and the Review Task remains Due.
- The contract covers conclusive Review failure: one Review FAIL evidence record, no successor Review Task, Current Milestone = Learning, and Highest Milestone Reached unchanged. A later fresh Independent pass cancels stale work and schedules a new Review 1.
- The contract covers an inconclusive response assessment: no pass/failure evidence, no milestone change, no cadence advance, and a new verified Fresh Equivalent attempt attached to the same Started Review Task.
- Public HTTP coverage extends the existing learner contract tests with Review collection, Due start, explicit cancellation in each unfinished status, reused submission, progress visibility, idempotency/conflict semantics, and strict absence of private projections.
- PostgreSQL recovery coverage extends the existing restart test through Scheduled, Due, Started, and completed Review states. It verifies the unfinished-task uniqueness constraint and recovery after evidence-producing transitions without duplicate evidence or successor work.
- Focused Concept Progress projector tests are retained because projection is a pure evidence fold and directly encodes ADR-0007/0008. They cover zero through four Review passes, Review failure from Independent, failure after a historical Durable milestone, a new Independent restart, non-qualifying evidence, and deterministic ordering by acceptance time.
- The existing `ApplyProfileContractTest`, `ApplyFlowUseCaseTest`, learner HTTP tests, PostgreSQL recovery test, persistence round-trip test, and scripted model fixtures are prior art. Review extends their contracts instead of introducing a second live-model oracle.
- The existing non-blocking Apply live smoke test may exercise the Review Blueprint as an optional provider-compatibility case, but it creates no evidence and is never required for CI acceptance.

## Out of Scope

- Adaptive spaced-repetition algorithms, FSRS/SM-2, model-selected intervals, per-learner cadence tuning, interval fuzzing, and operator-configurable cadence.
- Push, email, calendar, desktop, or mobile notifications; a notification service; daily review limits; backlog prioritization beyond due-time order; and review analytics.
- Manual snooze, reschedule, delete, force-start-before-due controls, or any Review Cadence mutation other than the explicit audited cancellation decision above.
- A new Review Profile, Review-specific Skill Stack, new Assessment or Verification model, new Rubric, or a second Task Package shape.
- Background task pre-generation, background Assessment, persistent Agents, introducing a second Learning StateGraph or Blackboard model, or running model work from the scheduler.
- New Concepts, new mathematical task families, Explain, Retrieve, Teach-back, Hint, or full remediation/Practice implementation. This spec emits the evidence-backed Learning-stage handoff after Review failure and relies on a future Teaching Profile to perform remediation.
- Substantive-clarification and hint UI. The current formal Apply task remains no-hint; ADR-0014/0015 behavior continues to govern future assistance and Flow-switch support.
- Authentication, learner account management, authorization, cross-learner privacy policy, or a general dashboard beyond the minimum reference UI needed to exercise Review work.
- Backfilling Review Tasks for Independent evidence created before this feature, maintaining compatibility with obsolete schemas or endpoints, or adding a migration compatibility layer.
- Changing the accepted Apply generation, Task Verification, response Assessment, selective Verification, canonical-answer confirmation, Artifact Store, or evidence visibility policies except where Review is added as an already-defined Attempt Purpose.

## Further Notes

- This spec operationalizes ADR-0004, ADR-0007, ADR-0008, ADR-0027, ADR-0028, ADR-0029, ADR-0042, ADR-0055, ADR-0064, and ADR-0066 through the repository's current application-owned Learning StateGraph and durable Apply capabilities. The scheduler remains model-free and does not wake the graph; learner Review commands resume the original Flow through the existing graph command boundary.
- The external product pattern is deliberately conventional: established spaced-repetition products expose scheduled work through a Due queue, keep overdue items actionable, and calculate later work after a review outcome. Kiln-AI adopts that proven work-item shape while keeping its accepted fixed evidence cadence instead of importing an adaptive scheduling algorithm.
- Review Task is coordination state; Accepted Learning Evidence is epistemic state. Keeping them separate is what allows scheduler recovery and milestone rebuilding without allowing time passage or a background process to claim mastery.
- Product and architecture discovery for this cadence is converged. The explicit cancellation and active-work rules in ADR-0070 are normative. Scheduler polling frequency and the concrete cancellation transaction/store method remain implementation details because they do not change any due time or acceptance behavior.
