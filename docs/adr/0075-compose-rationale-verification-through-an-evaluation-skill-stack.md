# Compose rationale corroboration through separate Evaluation Skill Stacks

When a Diagnostic's Trusted Primary-Answer Check proves the answer incorrect, an Applicable Rationale may rescue it only when both isolated Rationale Assessment and Rationale Sufficiency Verification confirm applicability; any semantic disagreement or uncertainty becomes Unconfirmed Diagnostic Performance without being mislabeled as learner failure. A Trusted Primary-Answer Check is repeatable and declared by the Task Blueprint, such as deterministic mathematical equivalence, a frozen answer key, or closed structural constraints; model agreement and `Cannot Decide` never establish the proven-incorrect precondition.

Both judgments run as Evaluation Profiles rather than reusing the Apply Teaching Skill Stack. V1 freezes Rationale Assessment to `evaluation.rationale-assessment@1.0.0` plus `verification.rationale-sufficiency@1.0.0`, and freezes the adversarial corroboration to `evaluation.counterexample-review@1.0.0` plus that same sufficiency Skill. The shared Verification Skill owns the cross-subject criteria, the distinct Evaluation Skills own normal versus counterexample-oriented judging methods, the Task Rubric and approved source basis own subject truth, and the Task Blueprint's Assessment Policy owns whether rescue is permitted. Neither Stack loads a Subject Skill or performs dynamic Skill routing.

Both Profiles use the Flow-frozen Strong Model Binding and receive separate instances of the same closed Rationale Evaluation Context: learner-visible task text, the complete rationale, only rationale-relevant Task Rubric criteria, necessary private expected-answer facts, bounded approved Source Passages, and Learner Locale. The context excludes the learner's primary answer, the Trusted Primary-Answer Check result, either evaluator's judgment and reason codes, prior Attempts or feedback, Learning State, and generator reasoning. The outer Assessment Policy owns invocation and combination, so neither evaluator is told that the rationale may rescue an incorrect answer.

Both Profiles return the same closed `rationale_evaluation/v1` result with one overall verdict, dimension checks for Rubric basis, task connection, and coherence, and closed reason codes without model reasoning. The Domain derives the verdict deterministically: all checks passing is `applicable`, any failed check is `not_applicable`, and no failed check with at least one inconclusive check is `inconclusive`; an inconsistent declared verdict is Model Contract Invalid. Only two committed `applicable` results permit the proven-incorrect Diagnostic Attempt to pass. A first result that is not `applicable` skips corroboration, while a second `not_applicable` or either semantic `inconclusive` produces the corresponding Conclusive Diagnostic Gap or Unconfirmed Diagnostic Performance Finding.

A missing rationale (`null`, empty, or whitespace-only) is structurally `not_provided`, produces a Conclusive Diagnostic Gap after a proven-incorrect primary answer, and invokes neither Evaluation Profile. Every non-empty rationale is evaluated as a whole; no keyword, phrase, hedge, or sentence-shape shortcut may classify it before Rationale Assessment, so hesitant language can still pass when the complete justification is sufficient.

Rationale evaluation produces two distinct non-passing Diagnostic Findings rather than one immediate Guard route. A proven-incorrect primary answer with a missing rationale or a definitive first `not_applicable` is a Conclusive Diagnostic Gap and may carry sanitized missing Rubric criteria and reason codes. An unresolved primary answer, any semantic `inconclusive`, or a first `applicable` that corroboration does not confirm is Unconfirmed Diagnostic Performance and carries only neutral Feedback Facts, never a claimed learner deficit. Conclusive Findings participate in the Plan's minimum-sufficient stopping decision. Unconfirmed Findings request a fresh Plan-authorized probe while budget remains; at the termination limit, Target uncertainty routes neutrally to Target Learning and Practice, while Required Supporting Concept uncertainty prevents direct post-Diagnostic Independent eligibility and produces a neutral recommendation that the learner may override into Target Learning. Neither creates Diagnostic Evidence, and both remain distinct from technical Unavailable Interaction.

Task Blueprints opt into this rescue behavior only through `diagnostic.primary-or-corroborated-rationale@1`, which requires a declared Trusted Primary-Answer Check and a rationale-relevant Task Rubric mapping. Diagnostic rationale is never required: a Blueprint that does not justify its value disables the field, with simple Prerequisite Readiness Checks doing so by default. When enabled, the learner projection states that rationale is optional and may help distinguish understanding from an execution error. The current polynomial Diagnostic replaces `diagnostic.final-or-applicable-rationale@1` with this cross-subject policy identity; the obsolete policy is removed without an alias, fallback, or compatibility mapping. Independent Test, Practice, and Review policies do not change, and no Diagnostic receives rationale rescue by default.

V1 integrates and regression-tests this policy only through the existing polynomial-differentiation Diagnostic. A non-mathematical Profile Contract fixture and any additional product Concept are deferred, so V1 establishes a subject-neutral Profile, Skill, context, and contract boundary but does not claim demonstrated cross-subject model quality.

The Evaluation Profile instructions, both Evaluation Skill Stacks, `rationale_evaluation/v1`, and the Rationale Evaluation Context schema contain no calculus-, derivative-, or polynomial-specific term or field. The current mathematical Task Package is projected at the evaluation boundary into generic task text, rationale-relevant Rubric criteria, expected-answer facts, Source Passages, and locale; all calculus truth remains in those task-owned facts rather than in the reusable evaluator artifacts.

The normal proven-incorrect rescue path makes at most two model calls, one for each Evaluation Profile. Each responsibility owns at most one same-binding, same-Profile, same-Stack, same-context contract repair using only normalized violations; a valid `not_applicable` or `inconclusive` is never retried semantically. Provider failure or timeout performs no hidden automatic retry and commits Unavailable immediately. The worst malformed-contract path therefore makes at most four calls before Unavailable, while a later learner-issued `retry_requested` belongs to ADR-0069's separate bounded Retry Chain.

The Assessment Policy combines channels as follows. A proven-correct primary answer passes that Diagnostic Attempt immediately and ignores the optional rationale. A proven-incorrect answer with no rationale or a first `not_applicable` is a Conclusive Diagnostic Gap; a first semantic `inconclusive`, or an initially `applicable` rationale not confirmed by corroboration, is Unconfirmed Diagnostic Performance; only two `applicable` results pass the Attempt. `Cannot Decide` never enables rationale rescue: the existing isolated primary-answer judgments must both confirm correctness or the result is Unconfirmed Diagnostic Performance. The outer Diagnostic Plan—not this per-Attempt Assessment Policy—decides whether to ask another Diagnostic task and when accumulated Findings authorize a Neutral Transition, Target Learning and Practice, or a Prerequisite Learning Recommendation. Every technical failure reaches Unavailable. No Diagnostic branch creates Learning Evidence.

Evaluation composition reuses the existing Manifest schema, Skill Registry, Loader, immutable SemVer identity, and content hash but not the Teaching `BundleStack` invariant. `BundleSlot` adds `EVALUATION`; the existing Teaching Stack still requires exactly one `ACTION`, while a new `EvaluationBundleStack` requires exactly one `EVALUATION` and one `VERIFICATION` and rejects every other Slot in V1. A dedicated `RationaleEvaluationPromptCompiler` assembles Profile, Evaluation Skill, Verification Skill, and response contract in that fixed order under its own budget; no universal cross-Profile compiler is introduced.

V1 acceptance uses deterministic scripted Profile and whole-Flow contracts. It covers correct-primary short-circuit, missing and plainly insufficient rationales, hesitant but complete rationales, every two-evaluator agreement and disagreement branch, `Cannot Decide`, contract repair, Provider failure, Unavailable Retry, Committed Evaluation Result reuse, command replay, PostgreSQL restart, and exactly-once learner state and Evidence effects. It also proves the generic evaluator artifacts contain no calculus-specific contract or instruction fields and that existing Independent, Practice, Review, and pre-delivery Task Verification policies remain unchanged. Live-model smoke tests are non-blocking and create no evidence; the deferred non-mathematical fixture is not a V1 acceptance requirement.
